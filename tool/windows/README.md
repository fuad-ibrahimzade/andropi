# Windows port toolchain (no Administrator account needed)

`flutter build windows` refuses to run without a Visual Studio installation,
and Visual Studio (or the Build Tools) cannot be installed without
Administrator rights. Everything here lives in this checkout, is driven by
`mise run release` (see `tool/release.dart`), and changes nothing in the
machine's global environment.

| Move | What it is |
| --- | --- |
| `shims/vswhere_shim.dart` | Compiled to `pfx86/Microsoft Visual Studio/Installer/vswhere.exe`. Flutter hardcodes that path (below `%ProgramFiles(x86)%`); the release task points `PROGRAMFILES(X86)` at `pfx86/` for the build only, so the stub answers with the path of the fake tree in `vs/`. |
| `shims/cmake_shim.dart` | Compiled to `vs/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe` - the only CMake entry point Flutter accepts. It rewrites Flutter's `-G "Visual Studio 17 2022" -A x64` into `-G Ninja -DCMAKE_TOOLCHAIN_FILE=tool/windows/toolchain.cmake` and passes everything else through to the real (mise) CMake. It also pins what a `--config Release` MSBuild run would otherwise decide: `-DCMAKE_BUILD_TYPE` (Ninja is single-config; the template's default would be Debug and its empty `$<CONFIG>` skips the release AOT build) and `-DCMAKE_INSTALL_PREFIX` (CMake's default prefix is `%ProgramFiles(x86)%/<name>` - the fake vswhere tree here), both exported by `tool/release.dart`; the `--target INSTALL` Flutter builds then bundles exe + DLLs + assets into `build/windows/x64/bundle/`, which the release zip packages. |
| `toolchain.cmake` | clang-cl + lld-link + llvm-lib, `/MD` runtime, `rc.exe` for `Runner.rc`. |
| `nuget_link_fix.cmake` | Injected by the CMake shim as `CMAKE_PROJECT_INCLUDE`. Gives Ninja a producing rule for `flutter_windows.dll.lib` (Flutter's own command omits it, MSBuild tolerates that, Ninja does not) and, once configure has seen every target, walks them all to (a) append `-Wno-unused-command-line-argument` / `-Wno-macro-redefined` / `-Wno-unused-function` *after* the template's `/WX` (clang-cl flags MSVC's legacy `/await`, `apply_standard_settings` redefines `_HAS_EXCEPTIONS=0`, and the pigeon generators emit unused functions - all fatal under `-Werror`), (b) drop the literal quotes from `/wd"4100"`, which clang-cl parses as an integer, and (c) replace the NuGet MSBuild `.targets` files that `local_auth_windows` links with the plain include directory they stand for - lld-link cannot read MSBuild files. |
| `shims/cppwinrt_shim.dart` | Compiled over NuGet's `cppwinrt.exe` by the release task. The real tool only locates the Windows SDK in the registry (empty here, no installer can run); the stand-in copies the projection the SDK ships pre-generated inside the xwin splat into the plugin's `include/` directory instead. |
| `xwin.exe`, `.xwin-cache/`, `splat/` | Fetched on demand: [xwin](https://github.com/Jake-Shadle/xwin) downloads the MSVC CRT and Windows SDK headers/libs straight from Microsoft and unpacks them into `splat/` - no installer, no elevation. |
| `pfx86/`, `vs/` | Generated by `dart compile exe` of the two shims; safe to delete at any time. |

The remaining pieces come from per-user installs named in
`tool/release.dart`:

```powershell
scoop install llvm                  # clang-cl, lld-link, llvm-lib, llvm-mt
scoop install windows-sdk-buildtools # rc.exe, mt.exe
```

CMake and Ninja are pinned in the project's `mise.toml`.

Two more adjustments live in `tool/release.dart` rather than here:

- **Plugin symlinks**: `flutter` links the plugins into
  `windows|linux/flutter/ephemeral/.plugin_symlinks`, which needs either
  Developer Mode or an Administrator token. Directory junctions (`mklink /J`)
  need neither, and `dart:io` reports them as links with matching targets, so
  the task seeds them before every build.
- **Pub cache paths**: `.flutter-plugins-dependencies` records the cache of
  whichever OS ran `flutter pub get` last. Alternating between Windows and
  WSL rewrites those paths, so the task translates them to the local pub cache
  before seeding junctions.

## Why not install Visual Studio?

Installing it writes to `Program Files`, registers services and sets
machine-wide environment - it is impossible for a standard user, and this
user account is one. The shim above is equivalent: the same sources, the same
Flutter engine artifacts, the same `windows/` runner, only the driver changes
(clang-cl instead of `cl`, Ninja instead of MSBuild).
